# Требования к системе CoGoal

## 1. Функциональные требования

### 1.1. Авторизация и профиль
1.1.1: Система должна позволять новому пользователю зарегистрироваться, указав email, уникальный публичный идентификатор, имя и пароль.

1.1.2: Система должна проверять уникальность email и уникального публичного идентификатора, а также соответствие пароля требованиям (минимум 8 символов) при регистрации.

1.1.3: Система должна автоматически авторизовывать пользователя и начислять стартовый баланс монет после успешной регистрации.

1.1.4: Система должна позволять зарегистрированному пользователю входить в аккаунт по email и паролю.

1.1.5: Система должна возвращать понятное сообщение об ошибке при вводе неверных учетных данных.

1.1.6: Система должна позволять пользователю изменять свое имя, аватар, email (с подтверждением) и уникальный публичный идентификатор в профиле.

1.1.7: Система должна отображать в профиле пользователя текущий баланс виртуальных монет, список полученных достижений и ссылку на раздел «История транзакций». 

1.1.8: Система должна позволять восстановить пароль путем отправки временной ссылки на email, срок действия которой ограничен (например, 30 минут).


1.1.9: Система должна предоставлять страницу публичного профиля, доступную любому зарегистрированному пользователю по username.


1.1.10: Система должна отображать на публичном профиле статистику (количество завершенных целей).


1.1.11: Система должна строго разграничивать доступ: приватные данные (email, точный баланс монет, пароли) не должны возвращаться API при запросе публичного профиля.

1.1.12: Система должна предоставлять пользователю раздел «История транзакций» в профиле, отображающий все финансовые операции по его счету.


1.1.13: Каждая запись в истории транзакций должна содержать: дату и время, тип операции (списание залога, начисление награды, возврат, штраф), сумму, связанный пакт/цель и статус операции.


1.1.14: Система должна предоставлять фильтрацию истории транзакций по типу операции и периоду (неделя, месяц, произвольный диапазон).


1.1.15: Система должна поддерживать пагинацию истории транзакций (по 20 записей на страницу) с сортировкой по дате по умолчанию.


1.1.16: Система должна позволять пользователю экспортировать историю транзакций в форматах PDF для бухгалтерской или личной отчетности.

1.1.18: Система должна вести полный аудит-лог всех финансовых операций с указанием времени и даты, IP-адреса инициатора и ID пользователя для целей безопасности и разбора спорных ситуаций.


1.1.19: Все финансовые операции должны быть идемпотентными — повторный запрос с тем же идентификатором транзакции не должен приводить к двойному списанию или начислению.


### 1.2. Цели
1.2.1: Система должна позволять пользователю создавать цель, указывая название, описание, категорию, дедлайн и сумму залога.

1.2.2: Система должна валидировать данные при создании цели: дедлайн должен быть в будущем, все поля заполнены.

1.2.3: Система должна позволять добавлять к цели один или несколько промежуточных этапов с собственными дедлайнами.

1.2.4: Система должна автоматически публиковать созданную цель в общую ленту для поиска напарников.

1.2.5: Система должна позволять автору редактировать название, описание и промежуточные этапы цели.

1.2.6: Система должна запрещать редактирование цели, если по ней уже заключен активный пакт.

1.2.7: Система должна позволять автору удалить свою цель только после подтверждения и при условии отсутствия активных пактов.

1.2.8: Система должна показывать уведомление пользователю, что если он хочет удалить цель, состоящую в пакте, то необходимо сначала разорвать пакт, и после можно удалить цель.

1.2.9: Система должна предоставлять предопределенный список категорий целей («Учёба», «Спорт», «Работа», «Здоровье», «Другое»). При создании цели пользователь должен выбирать одну категорию из этого списка. 

### 1.3. Пакты и проверка выполнения

1.3.1: Система должна отображать ленту публичных целей с возможностью пагинации, фильтрации по категории, поиска по названию и сортировки по дедлайну.

1.3.2: Система должна позволять пользователю отправить отклик на публичную цель другого пользователя.

1.3.3: Система должна позволять пользователю при создании цели пригласить напарника по его уникальному публичному идентификатору.


1.3.4: Система должна скрывать из общей ленты цели, по которым отправлено приглашение конкретному пользователю и ожидается его ответ.


1.3.5: Система должна отправлять приглашенному пользователю уведомление с деталями цели и кнопками «Принять» / «Отклонить».


1.3.6: Система должна автоматически отклонять приглашение, если приглашенный пользователь не принял решение в течение 48 часов с момента отправки.


1.3.7: При отклонении приглашения (явном или по таймауту) система должна предлагать автору цели:


Опубликовать анкету в общую ленту для поиска напарника;
Пригласить другого пользователя по username.

1.3.8: Система должна позволять получателю просмотреть детали приглашения в пакт и принять или отклонить его. При принятии система должна заблокировать (списать) залог с обоих участников.

1.3.9: Система должна отображать детальную информацию об активном пакте: участники, цель, этапы, история чек-инов, текущий статус и финансовые условия.

1.3.10: Система должна позволять расторгнуть пакт только при взаимном подтверждении обеих сторон, с возвратом залогов участникам.

1.3.11: Система должна автоматически завершать пакт по наступлении дедлайна: при полном подтверждении этапов начислять награду, при наличии неподтвержденных этапов — не возвращать залог.

1.3.12: Система должна позволять участнику пакта загрузить доказательство выполнения этапа (файл, ссылка или текст).

1.3.13: Система должна позволять напарнику принять доказательство или отклонить его, при этом при отклонении поле "Причина" является обязательным для заполнения.

1.3.14: Система должна поддерживать создание групповых пактов (до 5 участников), где каждый участник вносит свой залог.

1.3.15: В групповом пакте система должна засчитывать доказательство, если его принял хотя бы один другой участник, или отклонять, если хотя бы один участник его отклонил.

1.3.16: Система должна предоставлять пользователю до 3 попыток загрузки доказательства в случае его отклонения напарником, отображая счетчик оставшихся попыток.

1.3.17: Система должна автоматически принимать доказательство, если ни один из напарников не принял решение (принять/отклонить) в течение 48 часов с момента загрузки.

### 1.4. Коммуникация и уведомления
1.4.1: Система должна предоставлять текстовый чат, доступный только участникам активного пакта, с сохранением истории переписки.

1.4.2: Система должна генерировать и отправлять уведомления (на email-почту, указанную при регистрации) о ключевых событиях: новые приглашения, загрузка доказательств напарником, результаты проверки чек-инов, приближение дедлайна, завершение пакта.

### 1.5. Техническая поддержка
1.5.1: Система должна предоставлять форму для создания обращения в техническую поддержку. Пользователь указывает тему, описание проблемы, может прикрепить скриншот и привязать обращение к конкретному Пакту (если проблема с ним). Обращение сохраняется в системе в статусе «Открыто».


1.5.2: Система должна позволять представителю техподдержки (администратору) просматривать список обращений, менять их статус («В работе», «Решено», «Отклонено») и, в случае положительного решения по спору о списании, вручную начислять виртуальные монеты на баланс пользователя.
